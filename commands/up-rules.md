description: 以 caveman full 極限壓縮規則文件（CLAUDE.md / .claude/rules），只保 AI 可解析語意；同步檢查並維護專案根 README.md 供人類閱讀

精煉規則文件的唯一讀者是 AI——每次 session 全文載入，人類幾乎不看。因此壓縮強度直接拉滿到 `caveman` skill 的 **full** 等級，**不流失任何指令語意**，讓 AI 讀取更快更完整。

壓縮的對象是**冗詞、重複敘述、裝飾性說明**，絕非具體規則、約束條件或消歧義範例。

## 目標檔案

### 壓縮目標（caveman full，只保 AI 可解析語意）

- `CLAUDE.md`（專案根目錄）
- `./.claude/CLAUDE.md`
- `./.claude/rules/*.md`

存在哪個就處理哪個，缺的略過。透過 `@path` import 進來的檔案（如 `@CLAUDE.local.md`）**不主動壓縮**，除非它本身也落在上述清單內。

### 同步目標（人類可讀為準，不壓縮）

- `./README.md`（專案根）——見「步驟 5」

僅處理上述四種路徑。**不要**擴及 `skills/`、`commands/`、`settings.json` 或其他檔案。

## 執行流程

### 1. 蒐集脈絡

- 用 glob 找出實際存在的壓縮目標檔案，完整讀取每一個；確認 `./README.md` 是否存在。
- `git log --oneline -15` 與 `git diff` 檢視近期改動與開發方向。**這一步有明確任務**：找出近期新增的規則是否與既有內容**重疊、重複或矛盾**——這正是最該合併或刪除的部分。把找到的重疊點餵進後續壓縮，而非只是看過。

### 2. 建立指令清單（壓縮前）

逐檔提取一份**明確的指令清單**——每一條獨立的規則、約束、禁止事項、格式要求各列一項。這份清單是後續驗證不流失的基準，必須先建立、後改寫。壓縮強度提高後流失風險上升，此步更關鍵。

### 3. 逐檔精煉（caveman full）

先 Read `~/.claude/skills/caveman/SKILL.md`，套用其 **full** 等級規則改寫檔案內容。該檔不存在時，退回下方「caveman full 內嵌摘要」。

⚠️ 只改寫**檔案內容**。與使用者的對話與回報一律維持正常繁體中文——不要啟用 caveman 作為對話模式（caveman 的 Persistence 規則會持續整個 session）。

改寫時同步：合併第 1 步發現的重疊／重複規則；維持有助 AI 快速掃描的結構（標題、條列、表格、程式碼區塊）。

**caveman full 內嵌摘要**（fallback）：

- 刪：冠詞、填充詞（just/really/basically）、客套話、模糊修飾、裝飾性開場與結語
- 允許：片語式句子、短同義詞（fix 不寫 implement a solution for）
- 禁止：自創縮寫、裝飾性表格、emoji
- 標準技術縮寫可用：DB / API / HTTP
- 句型：`[thing] [action] [reason]. [next step].`

**語言**：允許把繁中規則改寫成英文 caveman 以進一步省 token。以下一律**維持原文**：專有名詞與專案代號（如 `COSS`、主機名、服務名）；路徑、指令、環境變數、檔名；規則本身**針對語言**的條文（如「以繁中回應」）——條文可用英文寫，但引號內的目標語言不能被改掉。

**逐字保留（一字不改，byte-for-byte）**：

- 程式碼區塊與 fenced block 內的所有內容
- 確切的指令字串（如 `git commit -m ...`）
- 格式範本／模板（如 commit message 結構、trailer 如 `Co-Authored-By: ...`）
- 消歧義用的正反範例（✅ 正確 ／ ❌ 錯誤）
- `@path` import 語法（如 `@CLAUDE.local.md`）——功能性語法，改寫即失效
- frontmatter 的 key 名稱與值（`description:`、`name:` 等）

只壓縮這些區塊**周圍的散文敘述**，區塊本身不動。

**不壓縮的場合**（移植自 caveman 的 Auto-Clarity 原則）：遇到下列情況，該條維持完整句子，不套 caveman——

- 多步驟且**順序有意義**的流程（刪連接詞後順序易被誤讀）
- 條件／例外分支（if / unless / 除非 / 僅當）
- 破壞性或不可逆操作的警告
- 壓縮後產生技術歧義

判準一句話：**壓縮後若存在第二種合理解讀，就不壓縮。**

### 4. 驗證未流失（壓縮後）

逐項比對第 2 步的指令清單：確認**每一條**指令在改寫後的內容中仍然存在（語意等價即可，不要求字句相同）。

⚠️ 由同一次改寫順手「自我感覺沒漏」不算驗證——必須拿清單逐條核對，否則會悄悄刪掉邊角規則卻回報成功。

caveman 專屬回讀檢查：確認片語化後順序／條件關係未被誤讀；確認技術詞、程式碼、error string、`@path` import 逐字未動；確認未自創任何縮寫。

### 5. README.md 同步

每次執行都檢查專案根 `./README.md`。

**有** → 讀取，比對本次精煉後的規則文件與實際目錄結構，判斷是否需更新：規則文件新增／刪除的章節是否該反映到 README；README 提到的 command / skill / 路徑 / 設定是否已不存在或已改名。無需更新時明說「README 已同步，未改動」，不要為改而改。

**無** → 新增，用上面「有」的同一套判斷寫內容，骨架參考：一句話定位專案；目錄結構樹（runtime 產物註明已 gitignore）；可用的 commands / skills 表格；設定重點；維護慣例。

README **不套 caveman**。目標讀者是人類：完整句子、正常標點、必要的表格與目錄樹。

### 6. 寫入並回報

直接用 Edit/Write 寫入檔案（**不要**自動 git commit，交由 `/now-push` 或使用者決定）。回報：

- 每檔的指令清單，逐條標記「保留 ✓」。
- 每檔行數／字數前→後對照與壓縮比（**作為觀察值陳述，不是追求的目標**）。
- 主要刪改點（合併了什麼、刪了什麼冗詞）。
- README.md 的處置結果（新增 / 已更新 / 已同步未改動）。

## 禁止事項

- 不新增任何原本沒有的規則或功能——此條僅約束壓縮目標檔案；README 屬補齊說明文件，不受此限。
- 不因某條規則「太長」就刪掉它——只刪冗詞，不刪語意。
- 不為了壓縮比而過度刪減；寧可保守也不流失指令。caveman full 是**風格**上限，不是壓縮率指標。
- 不改動壓縮目標與 README 以外的任何檔案，不自動 commit。
- 不以 caveman 風格與使用者對話或回報。
- 不對 README.md 套用 caveman。
- 不壓縮到需要重讀兩次才懂——AI 讀懂的成本也是成本。
